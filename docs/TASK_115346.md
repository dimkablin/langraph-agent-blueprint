Architecture requirements:

1. Storage backend
   Implement a durable storage abstraction with at least:

   * dev mode backend, if needed;
   * production-ready backend, preferably PostgreSQL;
   * clean interface boundary so storage can be swapped.

   If the project already has a `SessionStorage` abstraction, evolve it instead of replacing it chaotically.

2. Data model
   Design normalized persistent models for:

   * users
   * conversations / sessions / threads
   * messages
   * message parts, if needed
   * tool calls
   * tool results
   * stream/progress events
   * artifacts
   * LangGraph checkpoints or checkpoint references
   * conversation metadata
   * archive/delete state
   * timestamps
   * token/cost/latency metadata, if already tracked
   * optional memory references, but do not mix memory with raw chat history

   Minimum required fields:

   * stable IDs
   * `user_id`
   * `conversation_id`
   * `role`
   * `content`
   * `created_at`
   * `updated_at`
   * ordering field
   * soft-delete/archive flags
   * metadata JSON field where appropriate
   * schema version where useful

3. Multi-user isolation
   Every read/write must be scoped by `user_id`.
   Add tests proving user A cannot read, update, delete, archive, or continue user B’s conversations.
   Never rely only on frontend filtering for data isolation.
   Enforce ownership in backend/service layer.

4. LangGraph integration
   Integrate persistence with the LangGraph runtime:

   * conversation ID maps to LangGraph thread/checkpoint identity;
   * a user can resume a conversation and continue from previous state;
   * graph events are persisted durably;
   * final messages are persisted;
   * tool calls/results are persisted;
   * failed/interrupted turns are represented clearly;
   * server restart does not lose conversation history.

   Prefer clean LangGraph checkpoint integration if the project supports it.
   Do not store huge raw graph state in messages unless necessary.
   Keep checkpointing and chat transcript storage logically separate.

5. Streaming durability
   If the project streams events to the frontend:

   * persist important events during or at the end of the turn;
   * make streamed event IDs stable enough to deduplicate;
   * support reconnect/reload behavior where the frontend can reload the conversation and show the completed state;
   * do not duplicate messages after retry or refresh;
   * make writes idempotent where possible.

6. Batching and latency
   Revisit the previous SessionStorage batching work.
   The persistence layer should not perform excessive small writes per turn.
   Implement a safe batching strategy:

   * collect per-turn writes where possible;
   * flush atomically at turn completion;
   * still preserve critical events if a turn fails;
   * avoid losing the final assistant message;
   * avoid blocking the first token unnecessarily;
   * measure before/after.

   Required metric:

   * number of storage calls per normal turn before/after;
   * total turn persistence latency before/after;
   * at least one smoke benchmark with multiple conversations.

7. API/backend requirements
   Add or update backend endpoints/services for:

   * list conversations for current user;
   * get conversation by ID;
   * create conversation;
   * rename conversation;
   * archive conversation;
   * soft-delete conversation;
   * append/run a new user message in an existing conversation;
   * optionally search conversations;
   * optionally export user history.

   Use typed request/response models.
   Keep API contracts clean and documented.
   Do not expose internal graph state directly to the frontend.

8. Frontend requirements, if frontend exists

10. Reliability
